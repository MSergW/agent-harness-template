# Заготовка харнесу для AI-агентів

[English](README.md) · **Українська**

Готовий набір інструкцій, файлів стану й перевірок, з яким AI-агенти для коду — Claude Code, Codex,
Antigravity, GitHub Copilot — працюють над вашим проєктом як уважний колега. Його один раз копіюють у
репозиторій, а потім агент заповнює його за вашим власним кодом.

Він виріс із щоденної роботи над реальним продакшн-проєктом: кожне правило тут є тому, що колись його
відсутність коштувала часу.

## Навіщо

Без харнесу кожна сесія починається з нуля. Агент не знає правил проєкту, щоразу заново шукає ті самі
команди, каже «готово» після зміни, яку жодного разу не запускав, тихо послаблює тест, що падає,
забуває, що вирішили вчора, і перевіряє власний код з тими самими сліпими плямами, з якими його писав.

Харнес відповідає на кожну з цих проблем файлом або механічною перевіркою, а не довшим промтом:

| Проблема | Що робить харнес |
|---|---|
| Агент не знає правил | `AGENTS.md`: жорсткі правила з причиною кожного, карта коду, команди |
| «Готово» без доказів | одна команда `make check` і хук, що перед завершенням відповіді швидко перевіряє змінені файли |
| Контекст губиться між сесіями | `PROGRESS.md` (де ми зараз) і `docs/decisions.md` (чому так), їх оновлює скіл `handoff`, а хук показує на початку сесії |
| Автор перевіряє сам себе | `REVIEW.md` і субагент `reviewer`: рев'ю diff у чистому контексті, не більше двох кіл |
| Інструкції відстають від коду | `make check` червоний, поки лишилися незаповнені мітки або зламані посилання на скіли; скіл `harness-refresh` за запитом звіряє все з кодом |
| Кожен інструмент хоче своїх файлів | один `AGENTS.md` і одна `.agents/skills/` для всіх інструментів; Claude Code і Codex запускають ті самі скрипти хуків |

## Швидкий старт

Потрібні: `git`, `bash`, [`jq`](https://jqlang.org) (для хуків), [`ripgrep`](https://github.com/BurntSushi/ripgrep), `make` (не обов'язково).

1. Один раз отримати заготовку:
   ```bash
   git clone https://github.com/MSergW/agent-harness-template ~/agent-harness-template
   ```
2. Скопіювати її в проєкт. Нічого не перезаписується й не комітиться; файли, що вже існують,
   перелічені в `HARNESS_INSTALL.md` для злиття:
   ```bash
   ~/agent-harness-template/install.sh /шлях/до/проєкту
   ```
   Для невеликого проєкту (один бінарник, до ~5 тис. рядків, без веб-інтерфейсу) — з `--small`.
3. Відкрити проєкт в агенті й дати йому весь [FILL_PROMPT.md](FILL_PROMPT.md). Агент замінить кожну
   мітку `{{FILL: …}}` реальними даними з вашого коду, перенесе правила зі старих файлів інших
   агентів, зробить `make check` зеленим і звітує. Він також прочитає ваші попередні сесії Claude Code
   і Codex у цьому проєкті: ваші виправлення й повторювані помилки агента стануть правилами й
   перевірками, рішення з чатів потраплять у `docs/decisions.md` (секрети з переписок не копіюються).
4. Прочитати звіт і попросити закомітити.

Поки лишається хоч одна мітка `{{FILL`, `make check` червоний — недозаповнений харнес не пройде
непоміченим.

## Як іде задача з харнесом

1. **Початок сесії** — хук показує гілку, останні коміти, незакомічені зміни і стан із `PROGRESS.md`.
2. **Робота** — агент дотримується `AGENTS.md`: одна задача за раз, найменше рішення, що виконує
   задачу, нічого поза задачею не змінює (таке йде в `docs/plans/tech-debt.md`).
3. **Шари 1–2** — `make check`: форматування, vet і лінтер, потім тести. Зупиняється на першому
   червоному шарі й пише, що робити.
4. **Рев'ю** — субагент `reviewer` читає лише diff, у чистому контексті, за `REVIEW.md`.
   Блокувальні зауваження виправляють і перевіряють ще раз.
5. **Шар 3** — те, чого не досягають тести (інтерфейс у локальному прев'ю, тестовий сервер), і явний
   перелік того, що не перевірено.
6. **Передача** — `PROGRESS.md`, плани й рішення оновлюються, щоб наступна сесія почала з них.

## Що всередині

| Файл | Навіщо |
|---|---|
| `AGENTS.md` | головні інструкції для всіх агентів: жорсткі правила, критерії готовності, карта, команди |
| `CLAUDE.md` | `@AGENTS.md` і те, що є лише в Claude Code (хуки, скіли, субагенти) |
| `REVIEW.md` | рев'ю diff: що шукати (правила, яких не бачить `make check`, коректність змінених рядків), що ігнорувати, не більше двох кіл |
| `PROGRESS.md` | поточний стан для наступної сесії |
| `docs/decisions.md` | рішення, яких не видно з коду, з причинами |
| `docs/plans/` | плани на кілька сесій, техборг, ідеї |
| `scripts/check.sh` | єдина перевірка за `make check`: самоперевірки харнесу, Go/Node/Python за файлами-маркерами, власні перевірки проєкту |
| `.agents/skills/` | скіли: `verify`, `handoff`, `depth` (чотири питання перед великою задачею), `git-commit`, `harness-refresh` |
| `.claude/` | хуки (стан сесії, форматер після правки, перевірки перед завершенням, `rg` замість `grep`) і субагенти (`checker`, `log-reader`, `docs-sync`, `reviewer`, `committer`, приклад перевірки інтерфейсу) |
| `.codex/hooks.json` | ті самі хуки для Codex (без форматера: у `apply_patch` немає `file_path`). Codex запускає хуки проєкту лише після довіри: `/hooks` у CLI |

Невеликий проєкт отримує лише `AGENTS.md`, `CLAUDE.md`, `scripts/check.sh`, хуки й техборг; решту
додають пізніше з тими самими іменами, коли проєкт виросте.

Файли лише для агентів — англійською; файли для людей (`PROGRESS.md`, плани, рішення, повідомлення
комітів) під час заповнення пишуться мовою вашого проєкту.

## Windows

Усе працює в Git Bash (ставиться разом із Git for Windows), окремих `.bat`/`.ps1` немає. Один раз на
машині:

```powershell
winget install jqlang.jq BurntSushi.ripgrep.MSVC   # хукам потрібен jq; без нього вони мовчки вимикаються
git config --global core.symlinks true              # потрібен режим розробника (Параметри → Для розробників)
```

- `install.sh` запускати з Git Bash: `bash ~/agent-harness-template/install.sh /c/шлях/до/проєкту`.
- Без `make` — `bash scripts/check.sh`, це та сама перевірка.
- Установник додає в `.gitattributes` проєкту `*.sh text eol=lf`, інакше за `autocrlf=true` скрипти
  ламаються (`bash\r: not found`). Якщо їх уже викачано з CRLF: `git add --renormalize .`.
- Без підтримки symlink установник не створює `.claude/skills/*` і пише про це в `HARNESS_INSTALL.md`;
  `check.sh` на такому клоні пропускає перевірку посилань.

## Як підтримувати

- Раз на місяць або після великої фічі попросити агента запустити `harness-refresh`.
- Помилка, що трапилася двічі, стає перевіркою в `scripts/check.sh`, а не ще одним абзацом.
- Покращення, знайдене в одному проєкті, повертається в `files/` цієї заготовки, щоб наступний проєкт
  отримав його одразу.
